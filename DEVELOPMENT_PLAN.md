# План розвитку Workout Program

Статус: етапи 1–6 реалізовано та перевірено 29.10.2026.
Базовий сценарій: один користувач, основний пристрій — телефон, розміщення на GitHub Pages.

Результат реалізації: статичний PWA використовує IndexedDB, підтримує чернетки й завершені сесії, усі варіанти вправ, попередні результати, історію, JSON backup, офлайн-оболонку та графік прогресу. Доменні тести запускаються через `npm test`, наскрізний Chromium-сценарій — через `npm run test:browser`.

## 1. Що є зараз

- `index.html`: близько 119 KiB, 24 картки вправ, по 8 у днях A/B/C.
- У файлі разом містяться стилі, програма, пояснення техніки та довідкові розділи.
- Навігація між чотирма вкладками та днями побудована на прихованих radio inputs і CSS-селекторах. Картки використовують нативні `details/summary`.
- JavaScript, форми результатів, база даних, журнал тренувань і service worker відсутні.
- Уже є мобільна верстка, системні шрифти, темна тема та врахування safe area. Метатеги Apple самі по собі не забезпечують офлайн-роботу.
- `.github/workflows/static.yml` уже публікує статичні файли з `main` через GitHub Actions. Зараз в артефакт потрапляє весь репозиторій.
- `README.md` містить лише назву проєкту.

Висновок: наявний інтерфейс придатний для поступового доповнення журналом. Повна перебудова на SPA-фреймворку для цього обсягу не потрібна.

## 2. Рекомендоване рішення

Статичний застосунок: HTML + CSS + JavaScript ES modules, IndexedDB для журналу, JSON для перенесення даних, service worker для офлайн-доступу після першого завантаження.

| Частина | Рішення | Причина |
| --- | --- | --- |
| Інтерфейс | Наявний HTML, CSS і невеликі JS-модулі | Мінімум залежностей, поступове впровадження |
| Основні дані | IndexedDB | Структуровані записи, індекси, асинхронні транзакції |
| Налаштування UI | Невеликий запис налаштувань; за потреби localStorage | Не змішувати журнал із тимчасовим станом інтерфейсу |
| Резервування | Експорт та імпорт JSON | Перенесення між браузерами, телефонами й доменами |
| Аналітика | Таблиця історії, потім простий SVG-графік | Спочатку достовірні записи, потім візуалізація |
| Публікація | Наявний GitHub Actions → GitHub Pages | Статичні файли без серверного виконання |
| Офлайн | Service worker + локальні ресурси | Використання у залі без стабільного інтернету |

IndexedDB складніша за один JSON у localStorage, але краще відповідає журналу з редагуванням, історією та імпортом. Весь доступ до неї ізолювати в `storage.js`; не створювати додатковий ORM або універсальний framework.

Portable тут означає: каталог сайту можна розмістити на статичному HTTPS-хостингу, а історію перенести файлом. Режим запуску подвійним кліком через `file://` не є цільовим; локальна розробка відбувається через HTTP-сервер.

## 3. Користувацький сценарій

1. Вибрати день A/B/C і натиснути «Почати тренування». Система створює окрему сесію з датою.
2. Якщо є незавершена сесія, запропонувати її продовжити. Перемикання вкладок або дня не створює нового тренування.
3. У кожній вправі над формою показувати попередній результат: «26.10.2026 · 40 кг × 12; 40 кг × 10».
4. Початково показувати два рядки підходів відповідно до поточної програми. Дозволити додати або прибрати рядок.
5. Увести вагу та повторення, позначити підхід виконаним. Для вправ на час показувати секунди.
6. Введення автоматично зберігається як чернетка. Лише явно підтверджений підхід стає фактичним результатом.
7. Кнопка «Повторити попередні» копіює значення до чернетки; скопійовані підходи ще потрібно підтвердити.
8. «Завершити тренування» переводить сесію до історії. Можна завершити частково виконане тренування; пропущені вправи не отримують вигаданих результатів.
9. Наступного разу та сама вправа показує останні підтверджені підходи з попередньої завершеної сесії.
10. Через «Історію» можна відкрити тренування, виправити результат або переглянути прогрес конкретної вправи.

Приклад форми:

```text
Single-Arm Cable Lateral Raise
Минулого разу: 26.10 · 7,5 кг × 15; 7,5 кг × 13

Підхід    Вага, кг    Повтори    Виконано
1         [7,5]      [15]       [✓]
2         [7,5]      [  ]       [ ]

[+ Підхід]  [Повторити попередні]  [Історія]
```

Форму розмістити на початку `.exercise-body`, перед довідкою про техніку. Останній результат коротко показувати й у згорнутій картці. Поля і кнопки не вкладати в `summary`.

## 4. Ідентичність вправ: головне архітектурне рішення

Розділити місце вправи в програмі та саму вправу:

- `slotId`: місце у програмі, наприклад `a6` чи `c7`.
- `exerciseId`: незмінна ідентичність руху, наприклад `single-arm-lateral-raise`.
- `variantId`: конкретний варіант, наприклад `cable` або `dumbbell`.
- `equipmentKey`: конкретне обладнання, початково `default`; окреме значення, якщо користувач хоче розрізняти тренажери з різними ваговими шкалами.

Правила для поточного файлу:

- A6 і C7 — однакова Single-Arm Cable Lateral Raise. За однакових `variantId` та `equipmentKey` історія спільна незалежно від дня.
- A1 і C1 — різні варіанти тяги; автоматично об'єднувати їхні робочі ваги не можна.
- A3 містить Сміт / машину / штангу: вибір фактично виконаного варіанта має визначати історію.
- B7 містить Bayesian Cable Curl / Incline DB Curl: результати тримати окремо за варіантами.
- C8 містить Pallof Press і Calf Raise: усередині картки потрібні два окремі блоки запису. Для однакового Leg Press Calf Raise можна показувати результати з B8.
- Dead Bug не вимагає ваги; Side Plank як альтернатива потребує секунд. Не вимагати кілограми для кожної вправи.
- Для односторонніх вправ передбачити позначення «на бік» і можливість окремих результатів ліворуч/праворуч. Однакові значення можна вводити одним рядком «обидві сторони».
- Для гантелей явно вказувати, чи вага задана на одну гантель; для штанги — сумарну вагу. Ця домовленість є частиною варіанта і зберігається в історичному записі.

Ідентифікатори не отримувати з назви, індексу DOM або номера дня. Перейменування чи перестановка картки не повинні втрачати історію. Мапінг 24 карток і всіх доступних для запису альтернатив підготувати явно, без парсингу тексту бейджів.

## 5. Модель даних

Статичний каталог у `program.js`:

- `programVersion`, список днів і слотів;
- каталог вправ і варіантів;
- заплановані підходи, діапазон повторень/секунд, односторонність, спосіб обліку ваги;
- відповідність `slotId` → одному або декільком записуваним рухам.

IndexedDB, база з власною назвою `workout-program`, версія схеми 1:

| Object store | Основні поля |
| --- | --- |
| `sessions` | `id`, `dayId`, `programVersion`, `workoutDate`, `performedAt`, `createdAt`, `updatedAt`, `status`, `completedAt`, `revision` |
| `entries` | `id`, `sessionId`, `slotId`, `exerciseId`, `variantId`, `equipmentKey`, `exerciseNameSnapshot`, `variantSnapshot`, `sets[]`, `notes`, `updatedAt`, `revision` |
| `settings` | Одиниці, активна сесія, останній експорт, параметри інтерфейсу |

Один `entry` — результат конкретного руху в конкретному місці сесії. У C8 таких записів буде два. Вкладені `sets[]` достатньо прості; окреме сховище кожного підходу зараз не потрібне.

Підхід містить `id`, `order`, `kind` (`working` / `warmup`), `loadKg` або `null`, `reps` або `durationSeconds`, `side` (`both` / `left` / `right`), `confirmed`, `completedAt`. Тип навантаження й домовленість щодо ваги беруться зі збереженого варіанта. `null`, нуль і порожня чернетка мають різний зміст.

`workoutDate` — локальна календарна дата `YYYY-MM-DD`; її не отримувати обрізанням UTC-рядка. Часові мітки зберігати в UTC. `performedAt` — час виконання, який можна змінити для внесення старого тренування; `createdAt` — час створення запису в додатку.

Індекси: сесії за датою/статусом; записи за `sessionId` і складеним ключем `[exerciseId, variantId, equipmentKey]`. Фіксацію сесії та пов'язаних змін виконувати однією транзакцією. Унікальність запису контролювати за сесією, слотом і конкретним рухом.

## 6. Як обчислювати «минулого разу»

1. Знайти записи з тим самим `exerciseId`, `variantId` і `equipmentKey` у сумісних одиницях та способі обліку ваги.
2. Виключити поточну сесію, незавершені сесії, розминку, непідтверджені й порожні підходи.
3. Для поточного або заднім числом відкритого тренування брати лише результати, що передують йому за часом виконання. Для двох сесій одного дня врахувати `performedAt`.
4. Якщо попередня сесія пропустила цю вправу, шукати далі; не показувати «немає історії», коли є старіший результат.
5. Взяти найновішу відповідну сесію й показати всі її валідні робочі підходи разом із датою. Не зводити різні ваги до одного числа.
6. За відсутності даних показувати «Ще немає записів».

«Остання вага» є похідною від історії. Не підтримувати окреме незалежне поле `lastWeight`, яке може розійтися з журналом після редагування чи імпорту.

## 7. Надійність збереження і перенесення

- Чернетку записувати після зміни з короткою затримкою; підтвердження підходу — одразу. Завершення тренування чекає всіх поточних записів.
- «Збережено» показувати після завершення транзакції. При помилці залишати введене у формі та показувати можливість повторити запис.
- Не покладатися на `beforeunload`: на телефоні сторінка може закритися без нього. Після повернення відновлювати останню успішно збережену чернетку.
- Для кількох вкладок перевіряти `revision` у транзакції та повідомляти про зміну запису в іншій вкладці; не перезаписувати тихо новіші дані.
- Експорт JSON включає `schemaVersion`, `appId`, час експорту, сесії, записи та потрібні знімки назв/варіантів. CSV додати пізніше для аналізу в таблицях.
- Перед імпортом перевіряти формат, версію, числові значення та посилання на сесії. Спочатку показувати кількість записів і конфліктів.
- Повторний імпорт того самого файлу не створює дублікати: порівнювати стабільні ID. Для різного вмісту з однаковим ID дати явний вибір, а не довіряти лише годиннику пристрою.
- Імпорт застосовувати атомарно. Перед заміною даних запропонувати завантажити поточну копію. Некоректний файл не змінює базу.
- Передбачити версійні міграції схеми; невідому новішу версію експорту відхиляти з поясненням.
- Можна запросити persistent storage через `navigator.storage.persist()`, але резервна копія все одно потрібна.

GitHub Pages зберігає файли додатку; особистий журнал живе в браузері. Він не синхронізується автоматично між телефоном і ноутбуком. Очищення даних сайту може видалити журнал; приватний режим не призначений для довготривалого зберігання. В інтерфейсі потрібні доступні «Експорт», «Імпорт» і ненав'язливе нагадування про копію.

Дані прив'язані до origin. Зміна домену чи перехід між localhost і GitHub Pages потребує експорту/імпорту. Різні репозиторії під одним `owner.github.io` можуть мати спільний origin, тому назви бази та кешів мають бути специфічними для застосунку. Це розмежування назв, а не межа безпеки між сайтами одного origin.

## 8. Історія та прогрес

Перший реліз:

- список тренувань за датою, днем A/B/C і кількістю підтверджених підходів;
- деталі сесії з редагуванням, додаванням старого тренування та видаленням із підтвердженням;
- історія конкретної вправи: дата та всі фактичні підходи;
- фільтр варіанта виконання, щоб не порівнювати різні тренажери й гантелі як одну шкалу.

Наступний реліз:

- графік ваги за часом із повторами для відповідного підходу в підказці;
- повторення за фіксованої ваги та тривалість для вправ на час;
- обсяг `Σ(вага × повтори)` лише для порівнюваних варіантів із явно визначеним обліком сторін/гантелей;
- фільтр періоду та таблиця під графіком для точного читання значень.

Зростання ваги зі зменшенням повторень не позначати автоматично як однозначний прогрес. У MVP не потрібні автоматичні силові рекомендації чи приблизний 1RM для всіх вправ.

## 9. Структура файлів

```text
index.html                   # Наявна програма, техніка, оболонка журналу
assets/styles.css            # Стилі, винесені з HTML
js/app.js                    # Ініціалізація та події інтерфейсу
js/program.js                # Каталог, ID, варіанти, цільові параметри
js/storage.js                # IndexedDB, транзакції та міграції
js/workouts.js               # Сесії, валідація, пошук попереднього результату
js/history.js                # Історія і згодом графіки
js/backup.js                 # Експорт/імпорт і перевірка формату
sw.js                        # Кешування статичних ресурсів
manifest.webmanifest         # Запуск з домашнього екрана
icons/                       # Іконки для manifest і Apple touch icon
.github/workflows/static.yml # Публікація
README.md                    # Запуск, розміщення, копії даних
```

Спочатку залишити довідкові тексти в HTML. У `program.js` тримати параметри для запису й стабільні ID; форми та їхні цільові значення читати з каталогу. Існуючі бейджі підходів також оновлювати з цього каталогу, щоб не підтримувати дві різні програми. Картки зв'язати явними `data-slot-id`; не витягувати бізнес-дані з їхнього тексту.

Усі імпорти, ресурси та URL мають бути відносними (`./js/app.js`), щоб працювати під `/workout-program/`. Для розділів достатньо поточного перемикання або hash-навігації; маршрути з серверним fallback не потрібні. Додати клавіатурно доступні кнопки/вкладки та підписи полів, статус збереження оголошувати через `aria-live`.

## 10. Порядок реалізації

| Етап | Робота | Критерій готовності |
| --- | --- | --- |
| 1. Основа | Винести CSS; додати модулі, каталог, стабільні ID; описати варіанти та C8 | Наявна програма працює, усі картки мають явний мапінг |
| 2. Журнал | IndexedDB, створення/продовження сесії, форми підходів, валідація, автозбереження | Два тренування одного дня не затирають одне одного; чернетка відновлюється |
| 3. Попередні результати | Пошук попередніх підходів, зведення в картці, копіювання до чернетки | A6 використовує C7 за того самого варіанта; інший варіант має окрему історію |
| 4. Історія й копії | Журнал дат, перегляд/редагування/видалення, JSON export/import | Експорт відновлює журнал у чистому браузері без дублів |
| 5. Офлайн й випуск | Service worker, manifest, мобільна перевірка, документація, підготовка Pages-артефакту | Після першого завантаження можна офлайн відкрити сайт і записати тренування |
| 6. Аналітика | Графіки й фільтри на основі вже зібраної історії | Візуалізація відповідає фактичним підходам і варіантам |

Практична межа MVP — етапи 1–5. Графіки не повинні відкладати випуск надійного журналу. Перший наскрізний інкремент: A1 → запис двох підходів → перезавантаження → наступна сесія → попередній результат. Після перевірки цього сценарію поширити механізм на всі картки.

## 11. Перевірки перед випуском

- Ввести `40 × 12`, `40 × 10`, завершити сесію; у наступній отримати саме ці два підходи з правильною датою.
- Увести `7,5` та `7.5`: отримати однакове число. Порожнє поле не перетворюється на нуль; від'ємні, нечислові значення та дробові повторення відхиляються.
- Перевірити Dead Bug без ваги, варіант на секунди, різні результати сторін і два незалежні блоки C8.
- Пропустити вправу в останній сесії: отримати результат із попередньої сесії, де вона була виконана.
- Перевірити A6/C7, різні варіанти жиму, зміну назви й порядку карток.
- Перевірити незавершену сесію, скопійовані непідтверджені значення та розминку: вони не стають історичними робочими результатами.
- Відредагувати або видалити попередній результат: підказка та історія оновлюються узгоджено.
- Створити дві сесії за день, записати старе тренування, перевірити сортування й локальну дату біля півночі.
- Закрити й знову відкрити браузер, перевірити відновлення останнього успішного запису; помилка сховища не показує хибне «Збережено».
- Зробити export → import у чисте сховище, повторний імпорт, імпорт пошкодженого файлу, конфлікт ID та невідому версію.
- Перевірити конкурентну зміну з двох вкладок без тихого затирання даних.
- Перевірити Safari на iPhone та Chromium, цифрову клавіатуру, фокус і доступність кнопок.
- Відкрити `/workout-program/` напряму, перезавантажити, перейти в офлайн та оновити версію сайту: журнал зберігається.

Автоматизувати доменні сценарії пошуку попереднього результату й валідації імпорту, а також один браузерний сценарій запис → перезавантаження → наступне тренування. Інструменти тестування можуть бути dev-залежностями й не потрапляти в сайт.

## 12. Особливості GitHub Pages та офлайн-оновлень

- Використати наявний workflow; готувати артефакт лише з публічних файлів сайту, без тестів, внутрішніх документів чи резервних копій.
- Не зберігати особисті тренування або секрети в репозиторії та Pages-артефакті.
- Service worker розташувати в корені застосунку й обмежити його scope поточним каталогом; manifest використовує відносні `start_url` і `scope`.
- Кешувати лише ресурси цього застосунку; називати кеші з власним префіксом і версією. Не видаляти чужі кеші на спільному origin.
- Новий worker не активувати примусово посеред тренування. Показати «Доступне оновлення» і застосувати після збереження та згоди на перезавантаження.
- Очищення кешу старої версії не повинно очищати IndexedDB. Під час оновлення схеми обробляти відкриті вкладки та зберігати сумісність або просити їх перезавантажити.
- Перший доступ потребує мережі. Автоматична синхронізація між пристроями — окрема майбутня функція з зовнішнім сховищем і автентифікацією.
