# Evidence-Based Training Hub — журнал тренувань

Мобільний статичний застосунок із п'ятьма програмами для різних цілей і графіків. Він записує вагу й повторення кожного робочого підходу, показує попередній результат однакової вправи між сумісними програмами та зберігає історію прогресу.

## Каталог програм

- **Спина-Сейф 3×:** мінімальне осьове навантаження, три повноформатні тренування на тиждень.
- **Атлет 3×:** вільні ваги, базові рухи й три Full Body дні.
- **Сідниці та постава 3×:** акцент на сідницях, пропорціях, поставі та корі.
- **Upper / Lower 4×:** два дні верху й два дні низу.
- **Minimalist Busy Pro 2×:** два коротші Full Body дні для щільного графіка.

Категорії, програми, дні, картки, альтернативи та параметри підходів описані в `js/catalog/`. Щоб додати нову програму, створіть її модуль і зареєструйте його в `js/catalog/index.js`; окрему HTML-навігацію для неї створювати не потрібно.

## Локальний запуск

ES modules, IndexedDB і service worker потребують HTTP. Запускайте сайт із кореня репозиторію, наприклад:

```powershell
python -m http.server 8000
```

Після цього відкрийте `http://localhost:8000/`. Подвійний клік по `index.html` (`file://`) не є підтримуваним способом запуску.

## Навігація

Кнопка меню у верхній панелі відкриває розділи **Журнал**, **Історія**, **База знань** та швидкий перехід до акаунта. Меню однаково працює на телефоні й комп'ютері, закривається клавішею `Escape` або натисканням на затемнений фон і утримує клавіатурний фокус усередині, доки відкрите.

## Дані й резервна копія

Акаунт необов’язковий. У розділі **Акаунт і синхронізація** натисніть **Тренуватися без акаунта** та прийміть ризики локального зберігання. Після цього доступні журнал підходів, історія, прогрес, редагування, видалення та JSON export/import — навіть коли Supabase не налаштовано. Згода зберігається в цьому браузері.

Локальна історія зберігається лише в IndexedDB цього браузера. Очищення даних, інший браузер або пристрій можуть залишити вас без доступу до неї; вона не переноситься автоматично в акаунт. Регулярно експортуйте JSON. З акаунтом Supabase є джерелом правди для його окремої хмарної історії.

Після входу IndexedDB використовується як ізольований кеш і черга саме цього UUID. Офлайн-зміни позначаються «Очікує синхронізації» та надсилаються після повернення мережі. Вихід одразу приховує прогрес; якщо є незбережені в хмарі зміни, застосунок попереджає перед виходом.

Під час першого запуску цієї версії IndexedDB автоматично оновлюється до v3 та отримує транзакційну чергу `sync_records`. Старі тренування, підходи та ID зберігаються. Формат JSON-копій залишається v2; імпорт підтримує копії v1 і v2.

З акаунтом або після прийняття локального режиму доступні:

- експорт повної копії у JSON;
- імпорт JSON для відновлення або перенесення на інший пристрій.
- історія сесій і конкретної вправи;
- графік фактичної ваги, повторень або тривалості за 30/90 днів чи весь час.

Робіть експорт регулярно, особливо перед очищенням браузера, зміною домену чи телефона.

## Акаунти й Supabase

GitHub Pages не має власного backend. Для email/password акаунтів і приватної хмарної історії використовується Supabase:

Підключення до проєкту `rlxlelsnoggwnqtsabhh` уже задане в `js/cloud-config.js` публічним publishable key. Застосовані міграції збережено в `supabase/migrations/`, включно з протоколом окремих тренувань. Site URL і Redirect URLs у Supabase мають містити `https://vladkrasnikov.github.io/workout-program/` для підтвердження пошти та відновлення пароля.

1. Для нового проєкту застосуйте SQL-файли з `supabase/migrations/` у порядку назв. На вже налаштованому проєкті повторно їх не запускайте. [`supabase/session_sync.sql`](supabase/session_sync.sql) показує підсумкову схему нового протоколу. Публічні таблиці дозволяють власнику лише читання; запис проходить через RPC із серверною перевіркою revision і payload.
2. Скопіюйте публічні значення у `js/cloud-config.js`: `supabaseUrl` і `supabasePublishableKey` (або legacy `supabaseAnonKey`). `service_role` — серверний секрет; його **ніколи не можна** додавати у сайт, Git або браузерну конфігурацію.
3. `supabaseClientUrl` зафіксовано на офіційному browser-модулі `@supabase/supabase-js@2.119.0`. Застосунок завантажує його лише коли URL проєкту й публічний ключ заповнені.
4. У **Authentication → URL Configuration** задайте Site URL вашої GitHub Pages адреси, наприклад `https://<owner>.github.io/<repository>/`, і додайте цю саму адресу до Redirect URLs. Вкажіть її також як `emailRedirectTo` та `passwordResetRedirectTo` у конфігурації. Для локальної розробки окремо додайте `http://localhost:8000/`.
5. Увімкніть Email provider. Якщо підтвердження email увімкнене, після реєстрації користувач побачить стан очікування листа. Відновлення пароля повертає на дозволений redirect і відкриває форму нового пароля.

Кожен UUID акаунта має окрему локальну IndexedDB. База `workout-program` використовується для тренувань без акаунта й зберігає попередню локальну історію. Вона ніколи не під'єднується до акаунта автоматично. Після входу кнопка **Імпортувати старі локальні дані** виконує одноразовий явний імпорт: історія, маркер та черга записуються локально однією транзакцією. Хмарний маркер надсилається після тренувань, щоб повтор не створював дублів. Новіші локальні тренування після цієї міграції можна перенести через JSON.

Під час першого входу чистий кеш акаунта звіряється з хмарою; гостева історія не завантажується автоматично. Невідправлені локальні зміни зберігаються. JSON export/import охоплює поточний акаунт або локальну історію, залежно від режиму.

### Збереження та синхронізація тренувань

- `workout_sessions`: PK `(user_id,id)`, окремі `revision`, `format_version`, серверний `updated_at`, `deleted_at`, дата та програма; `payload` містить сесію, її вправи й підходи. Історичні назви та текстові ID збережені.
- `workout_settings`: окремі версії налаштувань. `activeSessionId` і `currentProgramId` залишаються на пристрої та не спричиняють хмарних конфліктів. Без локального покажчика можна продовжити найновіше незавершене тренування з хмари.
- `workout_apply_change`: атомарні CAS, валідація та перевірка власника з `auth.uid()`. `expected_user_id` має збігатися з авторизованим користувачем, щоб зміна входу не приєднала чужу локальну чергу до іншого акаунта. Незмінний `operation_id` зберігається в локальній черзі; компактна серверна квитанція робить повтор запиту безпечним навіть після зміни запису іншим пристроєм.
- `workout_get_changes`: клієнт передає карту ID/revision та отримує лише змінені payload. Незмінна історія не передається повторно. Карта версій усе ще росте з кількістю тренувань.
- Дані й generation/dirty/операція зберігаються однією транзакцією IndexedDB. Застосування хмарної зміни в тій самій транзакції перевіряє локальні зміни; воно не може затерти новий збережений запис. Відкрита чернетка також потребує явного вирішення конфлікту замість тихої заміни редактора.
- Різні тренування синхронізуються незалежно. Вибір local/cloud стосується лише показаних конфліктних записів і повторно перевіряє їхні версії. Видалення зберігає tombstone, щоб старий офлайн-пристрій не відновив запис автоматично.

Перший RPC нового клієнта атомарно переносить старий `workout_snapshots` конкретного акаунта в нові таблиці. Стара копія не видаляється; некоректні старі дані зупиняють перенесення з помилкою. Після переходу сервер забороняє старому клієнту записувати snapshot цього акаунта й просить оновити застосунок. До першого RPC старий клієнт продовжує працювати. Відкат до snapshot-клієнта після переходу потребує окремої зворотної міграції, оскільки нові зміни вже зберігаються в нових таблицях.

Tombstones і квитанції операцій не очищаються автоматично: видаляти їх без узгодженого строку підтримки офлайн-пристроїв небезпечно. Локальна черга не входить у JSON backup — він містить користувацьку історію, а імпорт створює нові локальні операції.

Для GitHub Pages публічне підключення також можна задати в **Settings → Secrets and variables → Actions → Variables**: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_REDIRECT_URL` (адреса сайту з кінцевим `/`). Під час публікації `scripts/configure-cloud.mjs` створює конфігурацію в `_site/js/cloud-config.js`. Скрипт відхиляє секретні ключі та неповну пару URL/ключ. Якщо URL/ключ порожні і в Actions, і у файлі, сайт підтримує локальні тренування, а хмарний вхід залишається недоступним. SQL-схему та Auth URLs потрібно налаштувати в самому Supabase за кроками вище.

## Перевірка

Для тестів IndexedDB встановіть зафіксовану dev-залежність `fake-indexeddb`; вона не входить до опублікованого сайту:

```powershell
npm ci --ignore-scripts
npm test
```

Наскрізні smoke tests запускають локальний HTTP-сервер і встановлений Chrome або Edge. Вони перевіряють каталог, responsive burger menu, згоду на локальне зберігання, запис підходів без акаунта, відновлення після перезавантаження, ізоляцію акаунтів та offline sync:

```powershell
npm run test:browser
npm run test:account-access
npm run test:pwa-upgrade
```

[`supabase/tests/session_sync.sql`](supabase/tests/session_sync.sql) перевіряє справжні SQL/RPC, RLS, перенесення snapshot, CAS, повтори операцій, валідацію та tombstones у транзакції з `ROLLBACK`. Запускається власником бази через SQL Editor або MCP; тест не надсилає листів і не залишає даних.

## Офлайн-режим

Перше відкриття потребує мережі. Після завантаження service worker кешує оболонку застосунку, локальні auth/sync модулі та безсекретну конфігурацію. Каталог відкривається офлайн, а раніше авторизований користувач може працювати зі своїм ізольованим кешем; зміни матимуть статус очікування синхронізації. Коли доступна нова версія, застосунок має завершити поточне локальне збереження перед її активацією.

## GitHub Pages

Workflow `.github/workflows/static.yml` запускається для `main`, збирає окремий каталог `_site` лише з публічних файлів і публікує його в GitHub Pages. У налаштуваннях репозиторію виберіть **Settings → Pages → Source: GitHub Actions**.

Усі URL застосунку відносні, тому сайт працює як project site за адресою виду:

```text
https://<owner>.github.io/<repository>/
```
